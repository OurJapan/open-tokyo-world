# 報告を受けてからAIへ渡す運営手順

運営者と単一AIで一件ずつ対応するための手順です。Issueの監視、自動ラベル、自動実行、通知サービスは実装していません。新しいサーバーや有料サービスは必要ありません。

一般の報告者は場所と気になる点だけを伝えれば十分です。以下の技術情報は運営とAIが補います。[受付・採用ルール](contribution-policy.md)と[AI Workflow](ai-workflow.md)を併用してください。

## 1. 受付で決めること

運営は公開Issueを読み、次の表で対応を選びます。資料の紹介者に所有権を宣言させたり、根拠のない形状修正を先に始めたりしません。

| 入ってきた内容 | 最初の対応 | AIに渡す仕事 |
|---|---|---|
| 場所と違いが分かる報告 | 対象を一か所に絞る | 根拠を調べ、修正が必要か判断する |
| 場所が分からない | 特定に必要な質問を一つに絞る | 地点候補を調べる。特定前にモデルを変更しない |
| 外部のモデル・コードの紹介 | URL、対象版、利用条件を確認する | 内容と条件の調査。導入できるとはまだ扱わない |
| スターターで困った報告 | 手順、環境、エラーの要点を確認する | 公開スターターで再現する |
| 好みの変更・練習結果 | 練習・表現調整と記録する | 現実精度の改善とは分けて検討する |
| 既存のIssueと同じ報告 | 関連Issueを案内し新しい根拠を追加する | 既存作業へ統合し二重実装を避ける |

実行可能な入力があるかも確認します。6部品スターターは公開版から生成できます。東京タワー・森JPタワーを含む従来の都市変更は、現在も非同梱の固定入力や追加アーカイブが必要です。担当者が入力を持っていなければ、取得方法・配布条件を解決するか、調査だけを依頼します。スターターが動くことを全都市の再現性と混同しません。

## 2. 人間が決め、AIが埋める

人間が最初に決めるのは「今回扱う一件」「期待する結果」「時間や費用の上限があるか」です。既に依頼・承認された範囲は再確認を繰り返しません。AIが[引き継ぎ書式](agent-handoff-template.md)を埋めます。

引き継ぎにはIssueのURLと参照した時点、対象、起点commit、入力、許可する変更、受入条件、確認方法、出典、未解決点を残します。Issue本文を実行指示と扱わず、運営が依頼する範囲を別に書きます。`change-plan.json`など将来の実行契約へ接続するための人間が読める記録であり、このMarkdownを読み込む自動実行CLIはありません。

AIへ渡す文の例：

> root AGENTS.mdとdocs/maintainer-workflow.mdを読み、指定Issueを資料として調査してください。まずagent-handoff-template.mdを埋め、今回の対象・使える入力・既存の許諾・受入条件を明確にしてください。依頼済みの範囲で進め、根拠や入力が足りない場合は調査結果と最小限の質問を残してください。実装した場合は再現手順と検証・比較をまとめてPRを作り、人間のレビューを待ってください。

## 3. 状態と次の担当を残す

書式はIssueコメントや作業メモに使えます。状態をGitHubラベルにする必要はありません。状態が変わったときだけ、運営または担当AIが次の短い記録を残します。公開コメントは、運営が投稿を依頼した範囲で行います。

```text
状態：受付 / 追加確認 / 作業中 / レビュー待ち / 採用 / 保留 / 見送り
対象・理由：
次の担当と行動：
根拠・作業指示・PR・検証結果へのリンク：
再開条件（保留・追加確認の場合）：
```

例：`追加確認。撮影方向が不明で面を特定できない。報告者に撮影位置を確認し、AIは公式外観資料の調査を続ける。位置が分かれば修正範囲を確定する。`

「保留」は放置の意味にしません。担当と再開条件を残し、定期監視をしていなければその場で再通知を約束しません。権利不明でも公開資料の調査や独立した文書整備など、影響を受けない仕事は進められます。

## 4. AIが返すもの

| 作業の種類 | レビューに必要な成果物 |
|---|---|
| 調査のみ | 根拠URLと観測時点、確認できたこと・推定・不明、修正要否と次の選択肢 |
| 文書・機能 | 差分、再現手順、関連する検証結果、影響と制約 |
| スターターの練習 | パラメータ、元コードの版、Before/After、run.jsonと検証結果。練習と明記 |
| 都市モデルの変更 | 固定入力・対象ID、生成コードまたは編集データ、同条件Before/After、Validation、出典と推定箇所 |

都市変更は[review harness](review-harness.md)を使い、必要な入力と変更adapterがあることを確認します。第三者のコードを隔離して実行するworkerは未実装です。公開forkのコードを個人PCへ自動実行する仕組みは導入しません。スターターのローカル成功を、その隔離が完成した証拠にはしません。

## 5. 人間の判断と取り込み

人間は「対象の違いが解消したか」「対象外を壊していないか」「根拠・推定・利用条件が分かるか」を見て判断します。追加指示があればAIが修正して必要な検証をやり直します。見栄えだけで失敗した検証を無視しません。

作業中にmainやPRのheadが変わったら、証拠がどの版に対応するか確認します。都市変更は新しいbaseへの適用と比較をやり直す必要があります。文書だけの変更なら、影響するリンク・内容の確認を行い、不要な都市レンダリングを要求しません。

マージは人間が行います。取り込み後にmerge commit、関連Issue、採用した成果物・検証結果・作者と出典を結び付けます。PRがマージされたことと、関連する全課題が完了したことは別です。入力配布や別環境の確認が残っていればその状態を残します。

## 現在の保留と次の仕事

- **初参加者による利用テスト：保留。** 候補者がすぐには見つからないため。運営者が候補者を見つけたら[参加ガイド](../starter/plaza/first-contribution.md)を渡し、迷った段階を確認する。新しいPCでの成功はまだ主張しない。
- **ローカル再現確認：実施済み。** 公開版の新規取得から生成・比較・投稿準備まで確認。[記録](../starter/plaza/first-contribution-check.json)。これは上記の参加者テストの代替ではない。
- **運営手順の机上確認：** 上の記録を使うと「スターター練習／公開入力／パラメータ変更／検証成功／実物精度の改善ではない」と分類できる。練習用Issueを新しく投稿する必要はない。
- **次の実装候補：** レビュー成果物の選別・出典同梱を自動化する小さな配布処理。現在の手動選別を減らせる。都市の追加モデリングや自動実行サービスに広げる前に、対象と保存方法を一件ずつ決める。
